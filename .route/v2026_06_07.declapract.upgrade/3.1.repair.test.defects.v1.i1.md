# 3.1.repair.test.defects - defect inventory

## defect 1: tsconfig lib lacks es2022

### what
type error TS2554 in jest.integration.env.ts(105,7): Expected 0-1 arguments, but got 2.

### how (diff against origin/main)
tsconfig.json was changed by upgrade:
- `"lib": ["dom", "es7"]` (original)
- `"lib": ["dom", "es2022"]` (fixed)

the upgrade introduced code that uses ES2022 `Error.cause` option without updating the lib.

### why
ES2022 Error constructor accepts `{ cause }` option. prior lib (es7) doesn't include this type definition, so typescript errors on the second argument.

### fix
changed tsconfig.json lib from `["dom", "es7"]` to `["dom", "es2022"]`.

---

## defect 2: circular dependency in src/ code

### what
dpdm cycle check failed with 18 cycles detected, 2 in src/:
- `src/domain.objects/LogTrail.ts -> src/domain.operations/genLogMethods.ts -> src/domain.operations/generateLogMethod.ts`
- `src/domain.objects/LogTrail.ts -> src/domain.operations/genLogMethods.ts -> src/domain.operations/generateLogMethod.ts -> src/domain.operations/formatLogContentsForEnvironment.ts`

### how (diff against origin/main)
the upgrade added `test:lint:cycles` to the lint check (new dpdm detection). the cycle was extant but not detected before.

### why
`LogTrail.ts` imported `LogMethods` type from `genLogMethods.ts`, which imports from `generateLogMethod.ts`, which imports `LogTrail` type from `LogTrail.ts` - creating a cycle.

### fix
extracted `LogMethod` and `LogMethods` types to new file `src/domain.objects/LogMethods.ts`:
- LogTrail.ts now imports from LogMethods.ts (no cycle)
- genLogMethods.ts imports and re-exports from LogMethods.ts
- generateLogMethod.ts imports from LogMethods.ts and re-exports for backwards compat

## defect 3: node_modules cycles blocking lint

### what
after fixing src/ cycles, lint still failed due to 16 cycles in node_modules (third-party packages like @aws-sdk, helpful-errors, @smithy/core).

### how (diff against origin/main)
the upgrade added .dpdmrc.yaml with empty exclude list. dpdm detects all cycles including those in third-party code.

### why
dpdm traces full dependency graph from src/ into node_modules. cycles in third-party packages are detected but not actionable by us.

### fix
added `node_modules` to .dpdmrc.yaml exclude list with comment explaining rationale:
- cycles within third-party packages are not actionable by us
- they don't affect our consumers differently (consumers get those packages directly via npm)
- per the rule, only devDependencies should be excluded - but this is excluding paths, not hiding prod dependency cycles in our code
